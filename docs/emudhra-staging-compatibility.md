# Published Linux 7.x compatibility verification

Verified on 2026-10-21 against the dedicated **staging** `http-proxy-test`
route `3e9aa468-47ca-4fc3-b61e-4049a3f92e34` (`45.79.155.229:8021`).
Production was not changed. No client was rebuilt or patched.

## Artifacts

Clients came from the `update_linux_amd64.bz2` assets of the official
[7.9.5](https://github.com/getlantern/lantern/releases/tag/7.9.5) and
[7.7.2](https://github.com/getlantern/lantern/releases/tag/7.7.2) releases.
The decompressed executables had these SHA256 hashes before and after testing:

| Release | Executable SHA256 |
| --- | --- |
| 7.9.5 | `fc62e4b3b5d457b43c7b5bbab7ff78d813c5046871ef5473ed0ee0bcfdac7293` |
| 7.7.2 | `bc8614165560b734c823760a30315530344f0415e695e1668a8f98db86f88ff7` |

The candidate was built from runtime revision `e335fd0` using Go 1.26.10,
`CGO_ENABLED=0`, `GOARCH=amd64`, and `-trimpath`. Its executable SHA256 was
`fec124ccfb6dfd9958e8646fff57e697d6cac7b49f89d66ae148754f81640092`;
the running staging process's `/proc/<pid>/exe` matched. The subsequent
workflow-only change does not change the candidate's runtime source.

## Method and results

The original binaries ran headless under Xvfb in an isolated Ubuntu 22.04
container with their required GUI/libpcap libraries. Their cached `proxies.yaml`
selected only the staging route. `-stickyconfig -readableconfig -proxyall`
prevented remote configuration replacement. A valid cached global config
set `MustProxy` rules for the test domains and disabled autoupdate. This
configuration change was necessary: a standalone partial global config is
rejected by these releases and causes fallback to their embedded config.

Every positive run required all of:

- Plain HTTP `http://example.com` and HTTPS `https://example.com` returning
  status 200 and the expected page body through the client's local HTTP proxy.
- `https://api.ipify.org` reporting **45.79.155.229**, rather than the test
  machine's direct address.
- Five further successful HTTPS requests with the same staging egress.

| Client | Normal route: Shadowsocks + smux | TLS + smux, API-issued ticket | Cached server-issued ticket after proxy restart |
| --- | --- | --- | --- |
| Linux 7.9.5 | PASS | PASS | PASS |
| Linux 7.7.2 | PASS | PASS | PASS |

For TLS, a temporary config on the same staging listener used fixtures
generated by lantern-cloud's actual `makeTLSSessionState`, `proxyini.Build`,
and `LegacyConnectConfig` paths. The binary required authenticated tickets.
The API-issued ticket was 121 bytes; the old client persisted a **new 123-byte
server-issued ticket**. Cached runs reused that state after restarting the
proxy. Client logs confirmed loading the persisted state. Thus both ticket
encodings were exercised through actual old client executables.

### Server-side packet verification

The tests were repeated with `tcpdump` on the staging VPS, filtered to TCP
port 8021 and the test machine's source IP. Wireshark 3.6.2 decoded the capture.
For both releases the verification matched the **exact bytes** of the ticket
in the client's persisted cache to a `NewSessionTicket` sent by the staging
server, then matched those bytes to a subsequent ClientHello after a proxy
restart. These were 123-byte Go-issued tickets, distinct from the 121-byte
API-issued bootstrap ticket.

The server echoed the ClientHello session ID and sent an abbreviated TLS 1.2
handshake: ServerHello, NewSessionTicket, ChangeCipherSpec, Finished, with no
Certificate or ServerKeyExchange. Resumed connections carried application
records in both directions, and the client-side HTTP/HTTPS/egress checks passed.
This verifies actual resumption, rather than merely successful connection with
a cached ticket that might have fallen back to a full handshake.

| Client | Server issuance → client reuse | Cached reuse after restart | Resumed application traffic |
| --- | --- | --- | --- |
| 7.9.5 | Capture stream 0 → 1 | Ticket from stream 2 offered in stream 4 | Renewed tickets in streams 5–8 |
| 7.7.2 | Capture stream 9 → 10 | Ticket from stream 9 offered in stream 11 | Streams 10–11 |

The [sanitized assertions](test-results/emudhra-staging-resumption.json)
contain the per-release result and stream identifiers. The private capture's
SHA256 is `e6fb3674047aef8c57e33cb110ba56459d4dc6f0a151fcc5f971f4e6a8bfa43a`.
Raw captures, ticket contents, session secrets, and route credentials are not
committed. The temporary TLS listener and capture were removed; the tested
candidate continues to use the route's original configuration.

A negative control flipped one byte in the API-issued ticket. A fresh 7.9.5
client then failed to proxy traffic and produced no egress response. This
checks ticket rejection and rules out a direct-connection success masking a
transport failure. Unit tests separately reject tickets issued under a
different key.

The original staging package was `http-proxy-lantern 0.0.0+22da31e9`, binary
SHA256 `1c1ac5b4fb3eb4ed88365c20cd6ec111288d9a267fd8391107c248f9c48f9132`.
The 7.9.5 baseline passed HTTPS/egress/repeated requests, but plain HTTP
returned 403 (`requested local address example.com:80 ()`). The candidate
returns 200 because it includes the origin-form Host handling fix already
present on main. This was recorded separately from the trust/ticket changes.

## Staging deployment and rollback

The installed package and original `/etc/http-proxy/config.ini` were preserved.
Only `http-proxy.service` was restarted. The candidate is selected through
`/etc/systemd/system/http-proxy.service.d/99-emudhra-canary.conf`; the temporary
TLS fixture is replaced by the normal route configuration after testing.
A timed rollback protected the test window.

To restore the original staging executable and restart that service:

```bash
timeout 120 mise -E staging x -- bin/lc routes ssh \
  3e9aa468-47ca-4fc3-b61e-4049a3f92e34 \
  sh /tmp/emudhra-staging-canary.sh restore
```

Run this from a lantern-cloud checkout. The restore script removes the canary
override, restarts the service, and verifies that the installed binary and
normal config match their saved originals. For production, use the normal
reviewed release/package rollout, not this temporary override.

Coverage is Linux amd64 for these two releases, TLS 1.2, and the two listed
transports. Other operating systems, architectures, transports, sustained
load, and a full installed-package/container rollout remain release gates.
